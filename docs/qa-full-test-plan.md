# Pakto: пълен план за тестване на критичните функции и крайните случаи

Съставен на 09.10.2026 по кода в `main` (след PR #4). Допълва `docs/qa-test-plan.md`: там е краткият списък преди пускането, тук е пълното покритие с крайните случаи. Числата (лимити, срокове, размери) и текстовете на грешките са взети от кода; ако кодът се промени, първо се сверяват те.

**Какво значи „критично“.** Тестът е тук, ако при провала му пада обещанието на Pakto: грешна сума, изгубено, подправено или двойно „да“, клиент, който не може да реши, чужд човек, който вижда или променя данни, или загубени данни.

**Приоритети**

| Ниво | Значение |
|---|---|
| **P0** | Блокира пускането. Грешни пари, загубено или подправено решение, изтичане на данни, системата не работи. |
| **P1** | Важна функция или защита. Пуска се само с известен и приет риск. |
| **P2** | Краен случай, който трябва да е разумен (ясно съобщение, без срив), но не чупи договорката. |

**Как се чете.** Всеки ред: ID, приоритет, стъпки, очаквано. „Отказ“ значи: действието не се записва, базата е непроменена, потребителят вижда съобщение на български (цитирано, когато е точно определено в кода).

## 0. Подготовка

### 0.1 Среда

- Локално: `pnpm db:up`, `pnpm db:migrate`, `pnpm db:seed` (по желание), `pnpm dev`. Писма: Mailpit на http://localhost:8025.
- Cron ръчно: `curl -H "Authorization: Bearer $CRON_SECRET" localhost:3000/api/cron/<email-outbox|offer-reminders|purge-accounts>`.
- Клиентът винаги е в **отделен браузър или профил** без служебна сесия. Порталът се проверява на 375 px и на компютър.
- Лимитите в паметта (вход, регистрация, отваряне на линкове, „нови линкове“, контактна форма) се нулират с рестарт на `pnpm dev`. Лимитите в базата (кодове, съобщения, „Платих“) не се нулират.

### 0.2 Хора

| Роля | Имейл | Права |
|---|---|---|
| Собственик А | `…+owner@` | всичко |
| Втори собственик А | `…+owner2@` | всичко (за смяна на собственик) |
| Координатор А | `…+office@` | шаблон „Координатор“ (всичко без `payments.record`), всички обекти |
| Специалист А | `…+field@` | шаблон „Специалист“ (`changes.draft`, `milestones.manage`), само обект 1 |
| Счетоводител А | `…+money@` | „По избор“: само `payments.record` и `finance.view`, всички обекти |
| Собственик Б | `…+ownerb@` | друга фирма |
| Клиент 1 | `…+client1@` | одобряващ в обект 1 и 2 |
| Наблюдател | `…+viewer@` | наблюдател в обект 1 |
| Клиент без имейл | само телефон | одобряващ в обект 3 |

### 0.3 Основен сценарий (ползват го повечето тестове)

Обект 1 „QA Кухня“, клиент 1. ОФ-001: 3 реда, ДДС 20 %, отстъпка 10 %, срок след 14 дни, условия 30/70, график от 3 етапа. Клиентът иска промяна → версия 2 → одобрение. После ПР-001 +170 € и +2 дни, ПР-002 намаление −50 €.

### 0.4 Местене на времето (SQL като `pakto_owner`)

```sql
-- Офертата да е изтекла:
update app.change_order_revisions set response_due_at = now() - interval '1 minute' where id = <revision_id>;
-- Кодът да е изтекъл:
update app.portal_otps set expires_at = now() - interval '1 second' where id = '<otp_id>';
-- Клиентската сесия да е неактивна над 30 дни:
update app.portal_sessions set last_seen_at = now() - interval '31 days' where id = <session_id>;
-- Изпратено преди N дни (за напомнянията):
update app.change_order_revisions set frozen_at = now() - interval '<N> days' where id = <revision_id>;
```
